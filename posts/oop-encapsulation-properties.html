Encapsulation and Properties

Why This Topic Matters

So far, any code outside our class could freely read or change any attribute. Even book.price = -500 would work fine, even though a negative price makes no sense. Encapsulation means controlling how the data inside an object can be read or changed, so the object can protect its own rules.

By the end of this post you will know:

  1. The underscore conventions Python uses for "internal" data
  2. How to use @property to add validation to an attribute
  3. How double-underscore name mangling works, and what it actually protects against
  4. How to make an attribute fully read-only

1. The Single Underscore Convention

A leading underscore, like self._price, is a message to other programmers: "please do not touch this directly, use the methods instead."

Python does not actually stop you from reading _price from outside the class, it is only a signal, not a real lock. But almost every Python programmer understands and respects this signal.

2. @property: Checking a Value Every Time It Changes

A @property lets you add a check to an attribute, without changing how someone else uses it from outside the class:

class Book:
    def __init__(self, title, price):
        self.title = title
        self._price = price

    @property
    def price(self):
        return self._price

    @price.setter
    def price(self, value):
        if value < 0:
            raise ValueError("Price cannot be negative")
        self._price = value

b = Book("Python 101", 500)
print(b.price)     # 500

b.price = 600       # goes through the setter
print(b.price)      # 600

b.price = -10
ValueError: Price cannot be negative

b.price still looks like a normal attribute from the outside, no brackets, just b.price. But every time it is read, it quietly goes through the @property method, and every time it is set, it goes through the @price.setter method. This is the main use of encapsulation in everyday Python: it still looks simple from the outside, but there is a rule checking it underneath.

Making a Value Read-Only

If you leave out the setter completely, the attribute becomes read-only, it can be read, but never changed:

class ReadOnlyPoint:
    def __init__(self, x, y):
        self._x = x
        self._y = y

    @property
    def x(self):
        return self._x

    @property
    def y(self):
        return self._y

p = ReadOnlyPoint(1, 2)
print(p.x, p.y)    # 1 2

p.x = 5
AttributeError: property 'x' of 'ReadOnlyPoint' object has no setter

This is useful for values that should stay fixed once an object is created. It works like a tuple being unchangeable, but applied to just one or two fields of an object, instead of the whole thing.

3. Name Mangling with Double Underscore

A double leading underscore makes an attribute harder to access from outside the class by accident:

class Account:
    def __init__(self, balance):
        self.__balance = balance

    def deposit(self, amount):
        self.__balance += amount

    def get_balance(self):
        return self.__balance

acc = Account(1000)
acc.deposit(500)
print(acc.get_balance())    # 1500

print(acc.__balance)
AttributeError: 'Account' object has no attribute '__balance'

This is not real security, Python simply renames the attribute behind the scenes (to something like _Account__balance), it does not truly hide it. But it clearly says "use the methods, not the raw attribute", and it stops small typos elsewhere in the code from silently creating a brand new attribute by mistake.

4. Practical Example: A Wallet with Validated Balance

class Wallet:
    def __init__(self, amount=0):
        self.__amount = amount

    @property
    def amount(self):
        return self.__amount

    @amount.setter
    def amount(self, value):
        if value < 0:
            raise ValueError("Amount cannot be negative")
        self.__amount = value

w = Wallet(100)
w.amount = 200
print(w.amount)    # 200

w.amount = -5
ValueError: Amount cannot be negative

Using @property together with a double-underscore attribute gives you both benefits at once: the value gets checked every time it changes, and there is a clear signal that the raw value should not be touched directly.

5. When to Bother with Encapsulation

SituationWhat to do
A simple attribute with no rules attached (like a name)Leave it as a plain attribute, no property needed
A value that must always stay within some range, or follow a ruleUse @property with a setter that checks it
A value that should never change after creationUse @property with no setter
Internal data other code should not touch directly, but does not need strict enforcementA single leading underscore, as a signal

Common Mistakes

MistakeWhat happensFix
Adding validation logic directly in __init__ but not in later assignmentsLater code can still set an invalid value directlyUse @property so every assignment, not just the first, goes through the check
Assuming double underscore fully hides an attributeIt is renamed, not hidden, and can still be accessed with the mangled nameTreat it as a strong convention, not real security
Naming the property method something different from the attributeThe getter and setter do not pair up correctlyBoth @property and @x.setter must use the exact same method name

Practice Questions

  1. What is the difference between a single underscore and a double underscore prefix?
  2. Why does b.price = -10 raise an error, even though price looks like a normal attribute?
  3. How do you make a property fully read-only?
  4. Does a double-underscore attribute stop all outside access completely?

Answers

  1. A single underscore is only a convention, "treat as internal". A double underscore triggers name mangling, making accidental outside access harder.
  2. Because price is a @property with a setter that checks the value before allowing the assignment.
  3. Define the @property getter, and do not define a matching @x.setter.
  4. No, it renames the attribute rather than truly hiding it, it mainly protects against accidental access, not determined access.
