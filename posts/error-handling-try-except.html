Error Handling with try and except

Why This Topic Matters

Every program meets problems it did not plan for: a user types text where a number was expected, a file is missing, a value is zero when you divide by it. Without any protection, Python stops the whole program and prints a long error message. That is fine while you are learning, but in a real program it is a bad experience.

Error handling lets your program notice a problem, deal with it calmly, and keep going. By the end of this post you will know:

  1. What an error (exception) is, and how to read one
  2. How to catch errors with try and except
  3. How to handle different errors differently
  4. What else and finally are for
  5. How to raise your own errors, and build your own error types

1. What is an Error?

1.1 Errors Are Called Exceptions

An exception is what Python creates when something goes wrong while your program is running.

If nothing catches it, the program stops immediately and shows the error. Here are the ones you will meet most often:

[1, 2, 3][5]         # IndexError: list index out of range
{"a": 1}["b"]        # KeyError: 'b'
"a" + 1              # TypeError: can only concatenate str (not "int") to str
undefined_var        # NameError: name 'undefined_var' is not defined
int("x")             # ValueError: invalid literal for int() with base 10: 'x'
1 / 0                # ZeroDivisionError: division by zero
open("nofile.txt")   # FileNotFoundError: No such file or directory: 'nofile.txt'

Each error has a type (the name before the colon) and a message (the text after it). The type tells you what kind of problem it is, and the message gives the details. Learning to read these two parts is half the job of fixing bugs.

1.2 Syntax Errors vs Exceptions

There are two broad kinds of problems:

KindWhen it happensCan try/except catch it?
Syntax errorBefore the program runs, Python cannot even read your code (for example, a missing colon)No, you must fix the code
ExceptionWhile the program is running, something goes wrongYes

This post is about exceptions, the ones that happen while the program is running.

2. try and except

2.1 The Basic Pattern

try:
    print(10 / 0)
except ZeroDivisionError:
    print("Cannot divide by zero")

# Cannot divide by zero

How it works: Python first tries to run the code inside try. If an error of the named type happens, Python jumps straight to the except block and runs that instead. The program does not crash, and the code after the block carries on normally.

If no error happens, the except block is simply skipped.

2.2 Getting the Error Message

Add as e to capture the error itself, so you can show or log the message:

try:
    n = int("abc")
except ValueError as e:
    print("Error:", e)

# Error: invalid literal for int() with base 10: 'abc'

2.3 Handling Different Errors Differently

You can stack several except blocks, one for each kind of error you expect:

def safe(value):
    try:
        return 10 / int(value)
    except ValueError:
        return "not a number"
    except ZeroDivisionError:
        return "zero not allowed"

print(safe("2"))      # 5.0
print(safe("abc"))    # not a number
print(safe("0"))      # zero not allowed

Python checks the except blocks from top to bottom and runs the first one that matches.

2.4 Catching Several Errors in One Block

If two errors should be handled the same way, put them in a tuple:

try:
    x = int("abc")
except (ValueError, TypeError):
    print("bad input")

# bad input

2.5 Catching Any Error with Exception

Exception is the parent of almost every error, so it catches them all:

try:
    1 / 0
except Exception as e:
    print(type(e).__name__)

# ZeroDivisionError

This is handy as a last safety net, but be careful. If you catch everything, you may hide real bugs, including typing mistakes in your own code. A good habit is to catch the specific errors you expect, and only use Exception at the very end, or where you log the problem.

try:
    int("x")
except ValueError:
    print("specific")
except Exception:
    print("general")

# specific

The specific one goes first. If except Exception came first, it would grab every error, and the specific block below it would never run.

3. else and finally

3.1 else, Runs Only If No Error Happened

try:
    n = int("5")
except ValueError:
    print("bad")
else:
    print("worked:", n)

# worked: 5

The else block runs only when the try block finished without any error. It keeps your "success" code separate from the code you are guarding.

3.2 finally, Always Runs

try:
    n = int("x")
except ValueError:
    print("bad")
else:
    print("worked")
finally:
    print("always runs")

# bad
# always runs

The finally block runs no matter what: if there was an error, if there was not, or even if the error was not caught. It is used for cleanup jobs like closing a file or a connection.

3.3 The Full Picture

BlockWhen it runs
tryAlways starts here
exceptOnly if a matching error happened in try
elseOnly if try finished with no error
finallyAlways, at the very end

4. Raising Your Own Errors

4.1 The raise Keyword

Sometimes Python will not see anything wrong, but you know the value makes no sense. An age of -5 is a valid number, but not a valid age. Use raise to create an error yourself:

def set_age(age):
    if age < 0:
        raise ValueError("Age cannot be negative")
    return age

try:
    set_age(-5)
except ValueError as e:
    print("Caught:", e)

# Caught: Age cannot be negative

This is how well-written functions protect themselves: check the input, and raise a clear error the moment something is wrong, rather than letting bad data travel deeper into the program.

4.2 Custom Error Types

For bigger programs, you can create your own error type, by making a class that inherits from Exception:

class InsufficientFunds(Exception):
    pass

def withdraw(balance, amount):
    if amount > balance:
        raise InsufficientFunds(f"Balance {balance}, tried {amount}")
    return balance - amount

try:
    withdraw(100, 500)
except InsufficientFunds as e:
    print("Failed:", e)

# Failed: Balance 100, tried 500

A custom error has a clear name that explains the problem, and lets other code catch exactly this situation without confusing it with a different ValueError.

5. Practical Examples

Example 1: A Safe Number Converter

def to_int(value, default=0):
    try:
        return int(value)
    except (ValueError, TypeError):
        return default

print(to_int("25"))     # 25
print(to_int("abc"))    # 0
print(to_int(None))     # 0

We caught TypeError as well as ValueError, because int(None) raises a TypeError, not a ValueError.

Example 2: Keep Asking Until the Input Is Valid

while True:
    try:
        age = int(input("Enter your age: "))
        if age < 0:
            raise ValueError("negative")
        break
    except ValueError:
        print("Invalid, try again")

print("Age:", age)

If the user types abc, int() raises a ValueError. If they type -3, our own raise creates one. Both are caught by the same except, and the loop asks again until the input is good. When it is, break leaves the loop.

Example 3: Skipping Bad Rows in a Loop

data = ["10", "x", "30", "", "50"]
good = []

for item in data:
    try:
        good.append(int(item))
    except ValueError:
        print("Skipping", repr(item))

print(good, sum(good))

# Skipping 'x'
# Skipping ''
# [10, 30, 50] 90

One bad value does not stop the whole job. This pattern is very common when cleaning messy data, which you will do a lot in machine learning.

Example 4: A Missing File

try:
    with open("missing.txt") as f:
        data = f.read()
except FileNotFoundError:
    print("File not found")

# File not found

This is the same idea we used in the file handling post.

6. Good Habits

  • Catch specific errors. except ValueError is better than except Exception, because it only handles what you expected.
  • Keep the try block small. Put only the risky line inside try, not your whole program. Then you know exactly which line failed.
  • Never write an empty except that hides the problem. An except block that does nothing makes bugs silent and very hard to find. At the least, print or log the error.
  • Do not use try/except to replace simple checks. If an if statement can check the problem clearly (like if b != 0), that is often easier to read.
  • Give clear messages. When you raise an error, say exactly what went wrong and what value caused it.

7. Common Mistakes

MistakeWhat happensFix
Putting except Exception before a specific exceptThe specific block never runsOrder them from most specific to most general
Catching every error and doing nothingBugs are hidden and hard to findCatch specific errors, and print or log the message
Wrapping the whole program in one big tryYou cannot tell which line failedWrap only the risky lines
Forgetting that int(None) gives TypeError, not ValueErrorThe error slips past your except ValueErrorCatch both: except (ValueError, TypeError)
Expecting else to run after an errorIt is skippedelse runs only when there was no error

Practice Questions

  1. What error does int("hello") raise?
  2. In a try / except / else / finally block, which part always runs?
  3. Why is it usually better to write except ValueError than except Exception?
  4. What does the keyword raise do?
  5. If the try block finishes with no error, does the except block run?

Answers

  1. A ValueError, because the text does not look like a number.
  2. The finally block, whether or not an error happened.
  3. It handles only the problem you expected, so real bugs elsewhere are not hidden.
  4. It creates an error on purpose, so you can stop the program (or jump to an except block) when a value makes no sense.
  5. No. The except block runs only when a matching error happens. If there is an else block, that one runs instead.
